# Локальный проект

SQL Knowledge хранит рабочую память непосредственно в `knowledge.sqlite` в корне проекта. `knowledge.toml` описывает проект и подключённые расширения; их manifest и миграции находятся в проекте. Первичные материалы и результаты остаются обычными файлами проекта, а зарегистрированные ссылки на них — в памяти. Общий пакет и сервер устанавливаются отдельно: копировать реализацию сервера в каждый проект не нужно.

Всегда выбирайте проект явно абсолютным путём, а не по случайному текущему каталогу. Инициализация создаёт новую память только по явному поручению; отсутствие или повреждение существующей базы не повод молча создать замену. Перед работой получите контекст, найдите относящиеся к задаче решения и ограничения. Отсутствие результата поиска не доказывает отсутствия факта.

Записывайте изменения типизированными операциями с источником, причиной, исполнителем и ключом идемпотентности; произвольный SQL допускается только для чтения. Различайте сообщения пользователя, наблюдения и выводы. Для активного знания сохраняйте долговременное основание, для принятого решения — авторизацию пользователя. При завершении значимого этапа выполните проверку проекта и устраните относящиеся к нему ошибки. Не сохраняйте секреты, cookies и чувствительные сырые логи.

Актуальная история живёт в SQLite. SQL-дампы не создаются и не обновляются после записи или завершения работы. Для переноса сохраните согласованную копию базы, manifest, расширения и нужные файлы; порядок и проверки описаны в [расширениях](extensions.md).

## Команды и подключение

При доступном установленном пакете команды принимают абсолютный путь перед подкомандой:

```sh
python -m sql_knowledge --project /absolute/project context
python -m sql_knowledge --project /absolute/project search --text "запрос"
python -m sql_knowledge --project /absolute/project query --sql "SELECT id, title FROM entities LIMIT 10"
python -m sql_knowledge --project /absolute/project check
```

По явному разрешению для нового проекта: `python -m sql_knowledge --project /absolute/project init --project-id PROJECT_ID --title "Название"`. `--title` необязателен. Новая база использует schema 1; schema 2 поддерживается как совместимость с существующими базами. `init` не перезаписывает существующую базу или manifest.

Шаблон конфигурации MCP для клиента, понимающего такой формат; замените пути реальными абсолютными путями к Python-окружению с установленным общим пакетом и корню проекта:

```toml
[mcp_servers.sql_knowledge]
command = "/absolute/shared-venv/bin/python"
args = ["-m", "sql_knowledge.mcp", "--project", "/absolute/project"]
```

Это шаблон, а не подтверждение установки пакета или доступности сервера в текущем чате. При недоступном MCP используйте CLI явно и сообщите об этом.

После изменения knowledge.toml или manifest расширения остановите работающий MCP для этого проекта. Примените миграции CLI, выполните проверку, затем запустите MCP заново с тем же явным project root. Hot reload manifest не поддерживается; старый сервер продолжает работать со старой конфигурацией и может отвергнуть новую версию. Миграции поддерживают DDL: создание таблиц/индексов и добавление колонок; INSERT/UPDATE/DELETE предметных строк внутри SQL-миграции запрещены, чтобы не обходить историю. Для изменения данных используйте typed операции.


## Несколько чатов и условное обновление

Чтение `catalog_get` возвращает `record.revision`. При изменении существующей сущности передайте эту revision в `envelope.expected_revision`; для связи/supersedes — версии остальных затронутых ID в `expected_revisions`. При conflict перечитайте запись и сформируйте новую правку с новым ключом. При потерянном ответе повторите исходный envelope с тем же ключом.

Все официальные записи проходят один локальный координатор; разные MCP-процессы читают независимо. Полный MCP `project_check` начинает job, затем `project_check_step` выполняет пакеты до `status=complete`; только `ok=true` подтверждает успех. Синхронный CLI `check` ждёт полного итога. Порядок обслуживания, persistent fence, `writer-stop`/`writer-start`, WAL и отмена — в [concurrency.md](concurrency.md).

Новый `init` также записывает поколение `instance_id` в DB/manifest. Сохраняйте сгенерированный manifest при переносе и не заменяйте его вручную образцом из документации.
