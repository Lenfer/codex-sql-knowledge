# Несколько чатов и обслуживание SQL Knowledge

> **Лабораторный инкремент receipts-v3.** Два дефекта ACK/storage из ревью audit4 исправлены и проверены на схемах 1/2. Прежние измерения audit4 остаются историческими: регрессия CLI и SLA на 1m здесь не переизмерялись. В рабочие проекты эта версия не внедрялась.

Один локальный `knowledge.sqlite` обслуживает несколько stdio MCP-процессов. Один writer-процесс принадлежит каноническому пути проекта; ОС-lock предотвращает двух лидеров. Проект/поколение проверяются клиентом и writer. Маленькие записи выполняются в общем writer без нового Python-процесса на каждую команду. Низкоуровневые `_core`, `_local` и `memory.mutate` предназначены для внутренних тестов/загрузки fixtures, не являются публичным обходным API записи.

## Чтение и запись

`catalog_get` возвращает revision сущности — последний event_seq, затронувший её. Сохраняйте эту revision в envelope.expected_revision при обновлении. Для relation_write передавайте expected_revisions для source_id и target_id. При создании нового объекта версия не обязательна; expected_revision=0 допустима. Extension upsert при изменении существующей строки требует revision связанной core-сущности. Storage register/reconcile/cleanup_plan для уже существующих файлов требуют expected_revisions по ID. Cleanup execute дополнительно защищается проверенным планом/токеном и fingerprint; это поэтапная файловая операция с intent/reconcile, а не общая транзакция SQLite+filesystem.

Одинаковый ключ и исходное содержимое возвращают квитанцию повтора без нового события, даже если версия позже изменилась. Ключ с другим содержимым отвергается. CAS проверяется внутри транзакции для core/extension. При conflict прочитайте свежие данные и создайте новое решение/ключ. При потере ответа сохраните исходный envelope и повторите его; не объявляйте timeout доказательством rollback.

Чтения не входят в очередь writer и не удерживают application mutex. Синхронные MCP-tools выполняются в потоках, поэтому один stdio adapter также обслуживает параллельные запросы. SQL-чтения имеют 5s VM deadline и кооперативную отмену; native I/O может задержать VM checkpoint. project_writer_status показывает число/возраст активных snapshots, включая overdue. Thread cancellation не обещает откат уже отправленной записи: для неё действует outcome_unknown/replay. Снимок чтения живёт один запрос. Каталог с after_id/expected_revision явно сообщает stale при изменении глобальной версии; это пагинация, а не write-CAS. Широкий FTS может быть существенно дороже карточки/узкого поиска; отдельно измеряйте размер результата и словарь запроса.

## Очередь и сбои

Локальный Unix socket расположен в приватном каталоге текущего пользователя `/private/tmp/sql-knowledge-UID/` (0700, socket0600). Это доверенный IPC одного пользователя, не сетевой сервер и не межпользовательская авторизация. Ограничения:256 ожидающих/готовящихся запросов,4MiB входных данных,32 запроса на клиента. Очереди клиентов обслуживаются по кругу. Запрос с истёкшим сроком до исполнения не мутирует базу. Время уже начатой операции может превысить клиентский timeout; результат тогда unknown. Очередь в RAM не является durable journal. Успех возвращается после commit; после kill неподтверждённую операцию повторяют по тому же ключу.

Хеширование storage выполняется до очереди в двух подготовительных потоках, fingerprint проверяется снова перед использованием. Переименование/изменение файла после подготовки даёт file_changed; повтор исходного ключа продолжает intent либо выдаёт receipt. Нет SQL-дампа, экспортирования всей базы или backup после каждой записи. Сервис завершается после 15s простоя (обычный idle exit не является maintenance fence). Следующая запись запускает его заново; сохранённые receipts остаются в БД.

## WAL и жизненный цикл

Новые проекты используют WAL + synchronous FULL; требуется исправленная SQLite>=3.51.3 (проверенная здесь 3.53.4). Старые базы при простом открытии не переводятся в WAL. WAL/SHM — рабочие файлы SQLite, их нельзя считать мусором или переносить только главный файл при активных соединениях. Для разрешённой копии живой базы применяйте SQLite backup API. Физический отказ питания/накопителя не эмулировался.

`python -m sql_knowledge --project /absolute/root writer-status` показывает writer/очередь. `checkpoint` выполняет PASSIVE checkpoint; обязательного TRUNCATE на каждый commit нет. Долгие читатели могут удерживать WAL; завершите/отмените их и повторите явное обслуживание. `writer-stop` закрывает вход, дренирует очередь и освобождает writer. Команда возвращает принятие drain и сохраняет maintenance fence, поэтому перед заменой файлов дождитесь освобождения OS-lock/исчезновения socket. Новые записи не могут автоматически запустить writer. После проверки восстановления выполните явный `writer-start`: он снимает fence только при освобождённом OS-lock и совпадающем поколении. `writer-status` показывает fence без автоматического оживления остановленного writer. Не восстанавливайте БД под живыми MCP/worker: остановите MCP и writer, сохраните разрешённый backup, проверьте manifest/идентичность/целостность копии, замените согласованную БД и заново запустите клиентов. Старые handles с прежним inode отвергаются; это ожидаемая защита, не команда автоматически принять чужую БД.

Миграция закрывает приём новых работ, дожидается уже допущенных работ, затем исполняется одной DDL-транзакцией; частичная DDL не видна читателям. Перед миграцией обновите manifest/скрипты, выполните `migrate`, проверьте checksum и данные, перезапустите MCP для обновлённого контракта расширений. Нельзя менять manifest/DDL одновременно с пользовательскими сообщениями без согласованного обслуживания. Каждая write-команда закрепляет hash manifest-контракта; старая MCP-сессия после смены контракта получает stale_contract и требует перезапуска. Core не предоставляет произвольный SQL-write endpoint.

## Полная проверка

MCP: project_check_start(files=true) → project_check_step(job_id,batch_size<=10000) до complete/failed → project_check_report. Проект, поколение, версия алгоритма и fingerprint снимка привязаны к job. Можно продолжить после перезапуска клиента; cancel помечает задачу отменённой. Физическая проверка выполняется отдельным worker с пределом 1h, логические фазы — пакетами с дисковым индексом истории/FTS/связей. Отчёт содержит покрытие/progress, а running не означает успех. В runtime 0.2.0.dev3 снимок/состояние `complete` job освобождаются автоматически после сохранения отчёта. Служебный кеш `.tmp/check-reports/reports.sqlite` хранит 20 ошибочных итогов и один успешный, без добавления в events. Незавершённые, занятые, keep и зарегистрированные копии сохраняются. Обслуживание выполняется при старте MCP, каждые 300 секунд и после complete; это код runtime, не Disk Budget и не ИИ. Initial backup/hash синхронны и для большой базы могут занять время; тяжёлый аудит не блокирует другие MCP-процессы или writer.

CLI: `check` ждёт итог; `check-start`, `check-step --job-id ID --batch-size1000`, `check-result --job-id ID`, `check-cancel --job-id ID` позволяют управлять порциями (аргументы с пробелами: `--batch-size 1000`). Подробное устройство и ограничения — docs/check-jobs.md исходного проекта.

## Совместимость квитанций storage

Новые intent фиксируют storage_key_version=2: фаза и ID кодируются раздельно. Готовые старые квитанции возвращают прежний результат; частичные старые операции проверяются по сохранённому payload и сущности. legacy_storage_collision означает неоднозначный старый шаг: операция остановлена без изменения истории. Сохраните исходный envelope и разберите эту операцию явно; новый ключ не является способом доказать завершение прежней операции.
