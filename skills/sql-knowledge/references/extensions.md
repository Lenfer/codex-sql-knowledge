# Расширения SQL Knowledge

Расширение хранит предметные данные рядом с общей памятью проекта и связывает их с сущностями ядра. Выбирайте наименьший подходящий механизм:

| Потребность | Место |
| --- | --- |
| Общая сущность, знание, решение, связь или зарегистрированный файл | Типизированные записи ядра |
| Необязательное свойство без отдельного жизненного цикла | `attributes` существующей записи, если её тип поддерживает это поле |
| Новое свойство существующей таблицы расширения | Версионированная миграция расширения и обновление его manifest |
| Самостоятельный набор предметных записей и связей | Новая таблица расширения с собственной миграцией и manifest |

Не добавляйте произвольные колонки в таблицы ядра ради проекта. Расширение принадлежит проекту, его таблицы имеют префикс пространства имён и внешние ключи к существующим сущностям ядра. Не храните секреты и чувствительные сырые журналы.

## Состав и версии

В корне проекта `knowledge.toml` задаёт идентификатор и версию схемы проекта и перечисляет включённые расширения с их версиями и путями к manifest. Каталог расширения содержит собственный `extension.toml` и упорядоченные SQL-миграции. Manifest объявляет имя, версию, namespace, миграции и таблицы: первичный ключ, колонку ссылки на сущность, разрешённые и обязательные поля. Имя и namespace должны совпадать, версия равна числу файлов миграций, а версии в двух manifest — совпадать. SQL-файлы миграций — исходный код изменения схемы, а не дамп содержимого базы. См. исполняемый пример в `examples/demo/extensions/demo/`.

Изменяя схему, добавьте новую миграцию и обновите manifest и версию; не переписывайте уже применённую миграцию. Применяйте миграции явно командой `python -m sql_knowledge --project /absolute/project migrate`: она выполняет их транзакционно и по порядку. Сервер MCP миграции не запускает. До применения ожидающих миграций операции расширения должны отказываться работать, чтобы код и схема не разошлись. Проверяйте результат на копии базы и сохраняйте совместимость существующих данных. Удаление или преобразование полей требует отдельного плана сохранения данных.

## Запись и чтение

Используйте MCP `extension_upsert(extension, table, row, envelope)` для записи и `extension_query(extension, table, limit=100, after_id=None)` для чтения. В `envelope` передаются метаданные `idempotency_key`, `actor`, `reason`, `source_ref`; данные строки передаются отдельно в `row`. Передавайте только объявленные поля правильных типов и существующую сущность ядра; constraints и внешние ключи SQLite дополнительно защищают целостность. Ссылка строки на сущность неизменяема после создания. У операции записи должен быть envelope с идентификатором идемпотентности, исполнителем, причиной и источником. Повтор идентичной операции с тем же ключом не должен создавать второй результат; для изменённого payload нужен новый ключ. Запись должна сохранять событие истории и квитанцию операции вместе с данными в одной транзакции. Ошибку проверки не следует обходить прямой записью в SQLite.

После изменения проверьте чтение записи, повтор с тем же ключом, отклонение некорректных полей и несуществующей сущности, историю и целостность базы. Чтение упорядочено по первичному ключу; используйте возвращённый `next_after_id` для следующей страницы. `limit` — от 1 до 100.

## Поиск

Поля таблиц расширений **не индексируются автоматически** полнотекстовым поиском ядра. Ищите по доступному описанию связанной сущности ядра или используйте явно реализованную интеграцию поиска расширения, если она существует. Наличие таблицы или manifest не означает, что её значения попадут в FTS.

## Перенос

Переносите согласованный снимок `knowledge.sqlite`, `knowledge.toml`, каталоги используемых расширений с manifest и всеми миграциями, а также нужные зарегистрированные файлы. Получайте согласованную копию базы штатным механизмом SQLite при остановленных писателях или через SQLite backup; не копируйте работающую базу без учёта WAL. На новом месте укажите явный корень проекта, проверьте доступность файлов, версии расширений, внешние ключи и целостность, затем сравните ожидаемые данные и историю. Общий пакет сервера устанавливается отдельно и не копируется в каждый проект. SQL-дамп не является штатным способом переноса.

## Полный пример: новая таблица

Готовый каталог для копирования — `examples/demo/extensions/demo/` библиотеки. Команда `examples/run_demo.py --project /absolute/new-demo` выполняет весь пример на новой базе через настоящий MCP.

Минимальный набор файлов локального проекта:

```text
my-project/
  knowledge.sqlite
  knowledge.toml
  extensions/demo/
    extension.toml
    001.sql
```

`knowledge.toml` (проектная идентичность должна совпадать с project-сущностью базы):

```toml
format_version = 1
project_id = "my-project"
schema_version = 1
[extensions.demo]
version = 1
path = "extensions/demo/extension.toml"
```

`extensions/demo/extension.toml`:

```toml
name = "demo"
version = 1
namespace = "demo"
migrations = ["001.sql"]
[[tables]]
name = "demo_items"
primary_key = "id"
entity_column = "entity_id"
columns = ["id", "entity_id", "value"]
required = ["id", "entity_id", "value"]
```

`extensions/demo/001.sql`:

```sql
CREATE TABLE demo_items (
  id TEXT PRIMARY KEY,
  entity_id TEXT NOT NULL REFERENCES entities(id),
  value TEXT NOT NULL
);
CREATE INDEX demo_items_entity ON demo_items(entity_id);
```

Применить миграцию явно:

```sh
python -m sql_knowledge --project /absolute/my-project migrate
```

После этого сначала создайте core-сущность `asset` через `entity_write`, затем вызовите MCP `extension_upsert`:

```json
{
  "extension": "demo",
  "table": "demo_items",
  "row": {"id": "one", "entity_id": "asset", "value": "Наблюдение"},
  "envelope": {
    "idempotency_key": "demo-one-v1",
    "actor": "operator",
    "reason": "Сохранить предметное наблюдение",
    "source_ref": "project:operator-observation"
  }
}
```

Чтение через MCP `extension_query`: `{"extension":"demo","table":"demo_items","limit":100}`. Для следующей страницы передайте возвращённый `next_after_id` как `after_id`. Запись с тем же ключом и payload возвращает `replayed:true`; изменение payload требует нового ключа. Эта строка не появляется в полнотекстовом поиске автоматически. Для поиска сохраните проверенное краткое описание в core-сущности отдельной типизированной командой.

## Добавить поле без потери существующей строки

1. Не менять применённый `001.sql`: его SHA256 закреплён в базе.
2. Создать `002.sql`: `ALTER TABLE demo_items ADD COLUMN score INTEGER NOT NULL DEFAULT 0;`.
3. В extension manifest задать `version = 2`, `migrations = ["001.sql", "002.sql"]`, добавить `"score"` в `columns`. В проектном manifest `[extensions.demo]` также задать `version = 2`.
4. На копии проекта выполнить `migrate`; прочитать строку `one`: прежний `value` должен сохраниться, `score` должен быть0. Сверить историю и `project_check`.
5. После проверки применить ту же миграцию к нужному проекту по его разрешению. При ошибке SQL или проверки схемы транзакция миграции откатывается; не подменять ошибку ручной правкой ledger.

Для новой предметной таблицы создать следующий SQL-файл и добавить новую секцию `[[tables]]`. Имя таблицы начинается с namespace (`demo_`), ключ — отдельный текстовый PK, `entity_column` — FK на `entities(id)`. Нельзя добавлять предметные колонки в core-таблицы через extension migration. Изменение типа/удаление данных не входит в этот минимальный контракт: сначала отдельно проектируется безопасная миграция и проверка сохранности.

После изменения knowledge.toml или manifest расширения остановите работающий MCP для этого проекта. Примените миграции CLI, выполните проверку, затем запустите MCP заново с тем же явным project root. Hot reload manifest не поддерживается; старый сервер продолжает работать со старой конфигурацией и может отвергнуть новую версию. Миграции поддерживают DDL: создание таблиц/индексов и добавление колонок; INSERT/UPDATE/DELETE предметных строк внутри SQL-миграции запрещены, чтобы не обходить историю. Для изменения данных используйте typed операции.


## Обновление существующей строки и аудит удаления декларации

Для изменения строки сначала получите revision её связанной core-сущности (`catalog_get`). В `extension_upsert.envelope` передайте `expected_revision` вместе с новым idempotency_key. Если передана revision при создании новой строки, она тоже проверяется. Связь строки с core-сущностью после создания неизменяема. Повтор того же исходного envelope возвращает receipt до новых проверок полей/revision; другой payload с тем же ключом отвергается.

Не удаляйте декларацию уже применённого расширения, чтобы скрыть его таблицы: полный аудит сверяет manifest с migration ledger, live tables и событиями, поэтому такой проект не получит ok=true. Отдельный механизм корректного удаления расширений в этот этап не входит. Перед изменением manifest выполните согласованное обслуживание и перезапуск MCP; после миграции старые write-клиенты получают stale_contract. Подробный lifecycle — в [concurrency.md](concurrency.md).

## Совместимость проектного словаря при миграции

Manifest может явно объявить legacy_artifact_kinds и legacy_predicates с name/target_kind/unique_source для сохранения старого словаря проекта. Это не меняет SQL CHECK существующей схемы и не разрешает переопределять ядро/supersedes; для новых предметных связей используйте таблицы расширения. Таблица с entity_kind допускает только владельца этого типа. Пример сохранения building/scene/primary_building — встроенный profiles/mavis; полная миграция описана в docs/mavis-migration.md исходного checkout. Старые строки и их события не преобразуются в другие kinds.
