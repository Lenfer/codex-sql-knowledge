# SQL Knowledge

> **Runtime 0.2.0.dev2.** Общая установка навыка и сервера не мигрирует базы существующих проектов. Старые проектные writers подключаются только через явно включённый адаптер совместимости; см. [legacy compatibility](references/legacy-compatibility.md).

Рабочая память — `knowledge.sqlite` в явно выбранном корне проекта. Используйте общий установленный пакет и сервер; не копируйте сервер в проект. `knowledge.toml`, проектные расширения и связанные материалы принадлежат проекту. Не создавайте и не обновляйте SQL-дампы.

Общий установленный CLI/Python и шаблон подключения: [references/installation.md](references/installation.md). Не использовать случайный системный Python или окружение чужого проекта.

## Перед работой

1. Определите абсолютный путь к корню нужного проекта и укажите его серверу или CLI явно. Не выбирайте базу по случайному текущему каталогу.
2. Получите контекст через MCP `project_context` и найдите относящиеся к задаче знания, решения и ограничения. При недоступном MCP явно используйте CLI `python -m sql_knowledge --project /absolute/project context` и сообщите об этом. Отсутствие результата поиска не доказывает отсутствия факта.
Перед записью подтвердите совместимость: в проекте должен быть knowledge.toml, а подключённый MCP должен публиковать project_writer_status и project_check_step. Одно имя project_knowledge не доказывает новый runtime. При legacy-подключении не обходите CAS и не переключайте его автоматически; нужна отдельная миграция/настройка.

3. Если база отсутствует или повреждена, сообщите об этом и диагностируйте проблему; не создавайте замену молча. Новую память инициализируйте только по явному разрешению.

## Работа с памятью

Используйте типизированные операции ядра для сущностей, знаний, решений, связей и регистрации файлов; произвольный SQL — только для чтения. В каждой записи указывайте уникальный ключ идемпотентности, исполнителя, причину и долговременный источник. Повтор того же envelope безопасен; изменённый payload требует нового ключа. Различайте `reported`, `observed`, `inferred` и неизвестное; активному знанию требуется основание, принятому решению — авторизация пользователя.

Для изменения существующей сущности сначала прочитайте `catalog_get.record.revision` и передайте `expected_revision` в envelope. Для связей и нескольких затронутых сущностей передавайте `expected_revisions` по ID; для supersedes нужна версия заменяемой записи. Разные новые объекты не используют одну глобальную revision. При `revision_conflict` перечитайте данные и согласуйте новую правку с новым ключом; слепой повтор старого изменения конфликт не устраняет. При `outcome_unknown` повторяйте исходный envelope с тем же ключом: commit мог уже состояться.

Все официальные записи CLI, MCP, library, extensions и storage metadata проходят общий локальный координатор проекта. Чтения используют независимые короткие соединения. WAL рассчитан на локальную файловую систему одного компьютера, сохраняется FULL; не переносите этот профиль на NAS. Очередь ограничена: `queue_full`/`queue_timeout` — явный отказ до записи, `outcome_unknown` требует проверки квитанции повтором. Не открывайте SQL write transactions между сообщениями чата. При обслуживании `writer-stop` сохраняет fence до явного `writer-start`; после изменения manifest старые клиенты требуют перезапуска. Подробности многопроцессной работы и обслуживания — [references/concurrency.md](references/concurrency.md).

После содержательного этапа фиксируйте цель, входы и версии, гипотезу, подход и основания, действия, проверку, результат, ограничения и следующий шаг. Сохраняйте неудачи и исправления; для успешного результата указывайте способ повторения. Регистрируйте полезные файлы, не помещая секреты или чувствительные сырые логи в память.

Для предметных полей сначала рассмотрите ядро и `attributes`, затем таблицы расширения. Меняйте расширения через versioned manifest и миграции, пишите и читайте через типизированные операции, соблюдайте внешние ключи и историю. Данные расширения автоматически в FTS не индексируются. Порядок и правила переноса — в [references/extensions.md](references/extensions.md), локальное устройство — в [references/local-project.md](references/local-project.md) установленного пакета.

## Завершение

Начните MCP `project_check`/`project_check_start`, затем вызывайте `project_check_step(job_id, batch_size)` до terminal status и читайте `project_check_report(job_id, offset, limit)`. Только `status=complete` и `ok=true` означают успешный полный аудит. `running`, `cancelled`, `failed` не являются pass. Пауза между вызовами допустима; job привязан к проекту, поколению и снимку. Полный аудит создаёт одну явную SQLite backup-копию для проверки; это не автоматический SQL-дамп после записи. Для синхронного CLI используйте `python -m sql_knowledge --project /absolute/project check` и исправьте относящиеся к работе ошибки. Если память или проверка недоступны, сообщите об ограничении. База хранит данные и историю непосредственно; SQL-дамп в конце работы не нужен.
